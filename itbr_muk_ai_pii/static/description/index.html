ServIAm Personal Data

Keeps clients' personal data out of the AI provider

What the MuK AI assistant (shown as ServIAm in Portuguese) reads from Odoo is masked before it reaches the AI provider, as LGPD asks. The people chatting keep seeing the real values.

  • Blocked models: HR/payroll and bank data cannot be read at all.
  • Field exposure: each field is allowed, tokenized (CPF, CNPJ, e-mail, phone, address, birth date, names of person contacts) or blocked, with admin exceptions.
  • Detector on the value: CPF, CNPJ, e-mail and phone numbers in any text sent to the provider become tokens.
  • Return path: tokens in the answer, in tool arguments and in approval previews are turned back into the real values.

Tokens are an HMAC of the value, with a key kept only on the server: the ODOO_AI_PII_KEY environment variable or the ai_pii_key option of the Odoo configuration file. Without a key, tokens are off.

Known limits

  • Names in free text are not detected: only CPF, CNPJ, e-mail and phone, by value.
  • Grouping by a name field tokenizes company and team names too.
  • Images, PDFs and attachments the user adds go unmasked (a notice is shown); documents the AI fetches ask for confirmation.
  • External MCP clients get blocks only: tokenized fields are dropped, no tokens.
  • In-chat exports keep tokenized fields (the file goes to the user); external exports drop them.
  • With this module installed, 5 upstream muk_mcp tests fail by design (external callers no longer receive email).
  • Not covered yet: muk_ai_subagents, muk_ai_chatter, muk_ai_automation, muk_ai_decision need a bridge before being installed together with this module (checked: muk_ai_chatter posts the stored answer, tokens included, as the note of a mention).
  • The module depends on muk_mcp_access.
